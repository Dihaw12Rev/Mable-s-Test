Request 1

Stale should mean unused, not unedited

"P4 uses the last edit time as the reason to be considered stale. Can we consider stale the ones that have had no enrolments in a year?"

Two earlier versions of this note were wrong, in opposite directions. The first said enrolment data did not exist — it tested nine per-workflow routes and passed the wrong identifiers, since the modern API calls a workflow 7870191 while the legacy API calls the same one 7023659. The second found the counts but concluded the dates were unreachable. They are reachable. They are just not in the API.

The dates live in HubSpot's own workflow export

The workflow listing in HubSpot is a CRM object, and exporting that listing produces a spreadsheet the API has no equivalent for. Four of its columns are the whole answer:

  • Last action on — the last time this workflow did anything to a record. This is the field the request was really asking for.
  • Enrolled last 7-days — how many records went through it this week, so a workflow can be checked as live rather than merely recently edited.
  • Currently Enrolled — records sitting inside it today, mid-sequence.
  • Current Issue Count — actions HubSpot is currently reporting as failing. 78 workflows here have at least one, 251 problems in total.

The audit now reads that file. Drop the export in as data/workflow-export.xlsx and every run picks it up. The one merged here was taken 4 September: 710 rows, 642 matched to the snapshot by workflow id, 68 built after the snapshot and carried in from the export alone, 4 in the snapshot and no longer in HubSpot.

What changed in P4, and it is not a small change

Stale now means no record has gone through it in a year. The list went from 198 workflows to 135, but the overlap is the interesting part:

  • 122 came off the list. They were flagged only because nobody had opened them in a year. They run every day — several last acted on 3 September. A correct workflow nobody needs to touch is not a problem, and asking the business to review 122 of them was going to burn the credibility of the whole exercise.
  • 59 went on to the list. These look maintained — edited in August 2026 — and have not moved a record since 2020, 2021 or 2022. The edit-date rule was hiding exactly the workflows that most deserve the question.
  • 16 have never enrolled a single record, and are switched on. Those sort to the top of the tab: in most cases the starting conditions can never be true, which is a bug rather than a retired process.

The oldest switched-on workflow last acted on 2 December 2019.

What is still not available

A per-record enrolment history, and a run date for the 119 workflows the export shows no activity for at all. Those read "never" where the export is certain and "not measured" where it is not — an unmeasured workflow and an unused one must never look the same in a column someone acts on. The API side of the finding also still holds: no endpoint returns a per-workflow run date, and property history records automation writes as enrollmentId:…;actionExecutionIndex:N, naming the enrolment rather than the workflow.

The export is a manual step, and it expires Automation → Workflows → export, with the four columns above added. It takes a minute and HubSpot emails the file. Everything in this section is as of the export date, not the audit date; re-export before the next review round or the run dates will quietly age.
Request 2

Fill rate on the unused fields

"Can we get for P6 a fill rate on those properties?"

Built, and it splits the list into four very different groups

Every one of the 2,249 fields now carries an exact count of how many records hold a value, against the object's total. Combined with request 3, the 332 the audit flagged as unreferenced turn out not to be one population at all.

The first row is the win: 154 fields can be archived with no further checking. The third is the save — those 54 would have been archived under the original guidance, and something would have broken.

Fields with no records behind them The quote object holds 195 properties and zero records. Fill rate is undefined there rather than zero, and the workbook leaves those cells blank rather than reporting 0% — an empty object is a different finding from an unused field.
Request 3

When a field was last written, and by what

"Can Claude export the property history to see when it was the last time those properties were updated on a record?"

Built as a sample, and the "by what" matters more than the "when"

HubSpot returns history one record at a time, so asking every record is not a report but a migration. Instead, the 200 most recently modified records per object are read — the right bias, because a field still in use shows up there first. 1,037 of the 2,249 fields had a write in that window.

Each field now reports its most recent write and what caused it, in plain terms: Automation, Integration sync, Form submission, Import, Someone typing. That last one is what the audit could never see before — a field maintained by hand looks identical to a dead one until you know who writes it.

What it found here

Of the 332 flagged fields, 54 were written within the last 12 months — 35 by an integration, eight by record merges, four calculated by HubSpot, four by form submissions and three by automation. Those are live fields that happen to sit outside any workflow, list or active form.

The riskiest single case: "Which distribution channels are you interested in?" is filled on well under 1% of contacts and was last written by a form submission the day before this was measured. On fill rate alone it looks abandoned. It is a working form field, and a low fill rate is exactly what a form field should look like — only the fraction of people who submitted that form will ever carry a value.

That case forced a change to how the verdict is calculated. Recency and source now outrank fill rate: a field written last month is in use at 0.1% fill, while a field at 40% fill last written in 2021 is a fossil. Ordering it the other way round marked live form fields as empty, which is the precise mistake this measurement exists to prevent.

A sampled date is a floor, not a ceiling A field may have been written more recently on a record outside the 200 sampled. Treat a recent date as proof of life; treat the absence of one as "no evidence found", never as proof the field is dead. The fill rate is exact — only the dates are sampled.

Where this leaves P4

The phase that previously said "nobody has edited these in a year" now says "nothing has gone through these in a year", which is a different list of workflows and a much better use of the review meeting.

The 68 workflows created after the snapshot are in there too, with their steps column reading "not read" — HubSpot's export names them and their activity, but only a fresh audit run can read their logic.
