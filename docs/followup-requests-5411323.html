Request 1

Stale should mean unused, not unedited

"P4 uses the last edit time as the reason to be considered stale. Can we consider stale the ones that have had no enrolments in a year?"

The premise is right

Last-edited answers "has anyone reviewed this?" Enrolments answer "is this doing anything?" The second is the better test for whether a workflow still earns its place, and the customer is correct that it is the more useful cut.

What we found

HubSpot does not expose workflow enrolment data to its API at all. Nine candidate endpoints were tested against a live active workflow — v2, v3 and v4 performance, metrics and enrolment routes. Every one returned 404. The enrolment counts visible in the Automation screen are not available programmatically.

What gets you the same answer

Every value on a record carries a history entry recording when it changed and what changed it. If a workflow's writes appear in that history, we can compute the last date it actually did something to a record — which is the question underneath the request, and arguably a stronger signal than enrolment. A workflow can enrol thousands of records and change nothing.

  • Last write by this workflow — the closest available equivalent to "last active".
  • Written by automation or by a person — the history distinguishes them.
  • Sampled, not exhaustive — read enough records to be confident, not all of them.
One thing still to confirm Whether the history entry names the specific workflow, or only says "automation", could not be verified — reading record history needs access this token does not have. It is a ten-minute check once that access is granted, and it decides whether this lands per workflow or only as "automation touched it". Worth confirming before it is committed to.

Recommendation

Keep both signals rather than swapping one for the other. A workflow that is busy but unreviewed is a different problem from one that is dormant, and P4 currently finds the first. Adding last-write splits those 179 into "running and doing something" versus "running and touching nothing" — the second group being the genuinely safe deletions.

Request 2

Fill rate on the unused fields

"Can we get for P6 a fill rate on those properties?"

Yes, and it closes the biggest gap in the audit

P6 currently lists 332 custom fields that no workflow, form or list references, with an explicit warning that this is not permission to delete — because a field filled in by hand on every record looks identical to a dead one. Fill rate removes that ambiguity.

How it works

One search per field, asking how many records have any value, against the total for that object. About 340 calls for all of P6, comfortably inside a minute at HubSpot's rate limits. It extends to all 2,249 fields for roughly four minutes if the fuller picture is wanted.

Fill rate alone still misleads A field written once during a 2021 import sits at 90% filled and is completely dead. Fill rate tells you how many records carry a value; it says nothing about when. Pair it with request 3 and the pair actually decides the question.
Request 3

When a field was last written

"Can Claude export the property history to see when it was the last time those properties were updated on a record?"

Per record yes, across every record no

HubSpot returns history one record at a time. There is no endpoint that answers "when was this field last written anywhere". Asking it of every record means one call per record — across this account's contact base that is a migration, not a report, and it would take days.

What is worth doing instead

Sample. For each field, read the history of a few hundred records that carry a value and take the most recent write. That answers the real question — is anyone still filling this in? — without pretending to a precision nobody needs.

  • Last observed write — a date, from the sample rather than the whole population.
  • Who writes it — automation, an import, an integration, or a person typing. This is the more useful half, and it is what tells you whether archiving is safe.
  • Honest about its limits — a sampled date is a floor. A field may have been written more recently on a record outside the sample.

What the three together give you

Each field in P6 would carry: how many records hold a value, when it was last written, and what wrote it. That turns the phase from a list requiring three manual checks per field into one that can actually be decided from the spreadsheet — which was the weakest point in the audit as delivered.

What is needed to build it

All three need permission to read records, not just field definitions. The audit deliberately asked for the narrower set, since it only ever needed the shape of the account, never its contents.

The trap that already cost us a round HubSpot issues a new access token whenever a private app's scopes change. Save the scopes first, then copy the token — a token copied beforehand keeps the old permissions and fails silently in exactly the same way as before.
